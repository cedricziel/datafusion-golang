# Design: wire-parquet-and-iceberg-insert

## Context

See proposal.md — Why. The engine contract this change implements is `add-table-provider-insert` (settled design, not yet built): a provider additionally implementing

```go
type WritableTableProvider interface {
    TableProvider
    InsertInto(ctx context.Context, op InsertOp, rows array.RecordReader) (uint64, error)
}
```

is detected at registration by type assertion and receives, exactly once per `INSERT` statement, the statement's fully planned input as a record reader in the table's registered schema, plus the mode (`InsertAppend`/`InsertOverwrite`/`InsertReplace`). Ownership of the reader passes to the provider (it must release it); the provider must commit or roll back before returning; the engine never filters modes (its design D5) — rejecting a mode is the provider's job and fails the statement like any other insert error. The correctness shape here differs from the pushdown wiring: there the risk was pruning away matching rows; here it is claiming a write mode the underlying API cannot deliver, or corrupting/losing data on partial failure.

Verified facts about the pinned libraries (from `go doc` and the vendored module sources, not memory):

**arrow-go v18.7.0, Parquet write side:**

- There is **no append-to-a-closed-file API**. The only Arrow-level writer is `pqarrow.NewFileWriter(arrschema, w io.Writer, props *parquet.WriterProperties, arrProps pqarrow.ArrowWriterProperties)` with `Write(rec arrow.RecordBatch)` per batch and `Close()` finalizing the footer — it produces a complete new file on a plain `io.Writer`. This matches the format: a Parquet file's footer at the end describes all row groups, so true in-place append to a closed file is not a thing arrow-go offers.
- `pqarrow.NewArrowWriterProperties(pqarrow.WithStoreSchema())` embeds the original Arrow schema (`ARROW:schema` key) in the file metadata; `pqarrow.FileReader.Schema()` prefers that stored schema on read, making the Arrow schema round-trip exact.
- Consequence: "append" for a single-file provider can only be *rewrite with old + new rows* (or a multi-file/directory table model, which this provider deliberately is not).

**iceberg-go v0.6.0, write side:**

- `Table.Append(ctx, rdr array.RecordReader, snapshotProps) (*Table, error)` and `Table.Overwrite(ctx, rdr, snapshotProps, opts ...OverwriteOption) (*Table, error)` exist; each is documented as "a shortcut for NewTransaction().Append()/Overwrite() and then committing the transaction". `Overwrite` with no filter option (default `AlwaysTrue`) deletes all existing data files and adds the new data — a full copy-on-write replacement — in **one** transaction commit (`table/transaction.go:1138-1195`).
- The commit path requires a catalog: `Transaction.Commit` → `Table.doCommit` (`table/table.go:374`) calls `t.cat.CommitTable(...)` where `t.cat` is the table's `CatalogIO` (`LoadTable` + `CommitTable`, `table/table.go:73-76`). A table opened via `table.NewFromLocation(..., cat)` stores whatever `cat` it was given — and `providers/iceberg`'s metadata-location path passes **nil** (`iceberg.go`, `loadTableFromLocation`), so `Append`/`Overwrite` on that path would dereference a nil interface. There is no filesystem-only commit fallback in v0.6.0. Independently, even a hypothetical commit would be invisible to this provider: it re-reads the one pinned `metadata.json` path per scan, and Iceberg commits produce a *new* metadata file — with no catalog tracking "current metadata location", the next read cannot find it.
- The commit is atomic-by-construction: data files and manifests are written first, then `CommitTable` performs the metadata swap (with built-in refresh-and-replay retries on `ErrCommitFailed` commit conflicts, and no retry on unknown-state errors). A failure before or during commit leaves the current snapshot untouched; already-written data files become unreferenced orphans, never visible to scans.
- Partitioned writes are supported: `recordsToDataFiles` (`table/arrow_utils.go:1504`) routes to `unpartitionedWrite`, `clusteredPartitionedWrite`, or a fanout writer based on the table's partition spec.
- Input schema resolution: `recordsToDataFiles` converts the reader's Arrow schema via `ArrowSchemaToIceberg(sc, false, nameMapping)` where `nameMapping` is derived from the table's own current schema (`meta.CurrentSchema().NameMapping()`, `arrow_utils.go:1532`). If the Arrow fields carry embedded field-id metadata it is used (and a *partially* present id set panics-converted-to-error); with no ids at all, fields resolve **by name** through the mapping. Field names in the registered schema are the Iceberg field names verbatim (the provider derives its schema with `table.SchemaToArrowSchema`).
- `catalog.Catalog` (the interface `NewTableProviderFromCatalog` takes, from `add-iceberg-catalog-client`) includes `LoadTable` and `CommitTable`, so a catalog-loaded `*table.Table` carries a working `CatalogIO` and the whole `Append`/`Overwrite` path is available. The in-repo tests already exercise exactly this: `providers/iceberg`'s fixtures are built with `catalog/hadoop` `CreateTable` + `Table.Append` (`iceberg_test.go`, `pushdown_test.go`, `catalog_test.go`) — including partitioned tables — so the write path is proven against the pinned version, on the local filesystem, with no catalog *service*.

**Existing provider shape being extended:** both providers are stateless-per-scan (fresh `file.Reader` / fresh `load()` per scan, design D4 of `add-parquet-and-iceberg-table-providers`); the Iceberg provider's catalog path re-resolves the table through `cat.LoadTable` on every scan (from `add-iceberg-catalog-client`), which is what makes read-after-write fall out naturally there.

## Goals / Non-Goals

**Goals:**

- Honest mode support only: each provider implements exactly the modes its real write API delivers correctly — Append + Overwrite for Parquet (as atomic rewrite) and for catalog-backed Iceberg (as native snapshot commits) — and rejects the rest with clear errors.
- Atomic-or-nothing visible effect per insert: a failure at any point leaves the Parquet file byte-identical and the Iceberg current snapshot untouched.
- Read-after-write within the same provider instance and session, with no schema drift.
- The same testing discipline as `wire-parquet-and-iceberg-pushdown`: dedicated adversarial tests for the failure-atomicity and mode-rejection logic, plus end-to-end insert-then-read and differential tests per provider.

**Non-Goals:**

- **Replace mode, both providers**: `REPLACE INTO` implies key-based upsert semantics; neither a bare Parquet file nor this Iceberg provider has key metadata to replace on, and faking it as append or overwrite would silently lie about semantics. Rejected with a clear error (expected and normal per the engine design's D5).
- **Writes on the Iceberg metadata-location path**: ruled out by the library (nil `CatalogIO` → no commit channel) and by semantics (a pinned `metadata.json` can never observe a new snapshot). Callers who want catalog-less local writes use `NewTableProviderFromCatalog` with `catalog/hadoop` — filesystem-backed, no service, already the fixture path in this repo's tests.
- Multi-file or directory-based Parquet tables (the provider wraps one file, unchanged), and preserving a rewritten file's original encoding details (compression codec, bloom filters, row-group layout are the writer's defaults — data is preserved exactly, encoding is not; a file whose row groups carried bloom filters loses them on rewrite, which affects future scan pruning *effectiveness*, never correctness, since absent bloom filters always mean "keep").
- Cross-process / external-writer coordination for Parquet (single-writer file, as on the read side), and Iceberg multi-writer conflict semantics beyond iceberg-go's own commit-conflict retry.
- Schema evolution via inserts, `DELETE`/`UPDATE`, and snapshot properties configuration.

## Decisions

**D1 — Parquet Append and Overwrite are both "write a complete temp file, then atomically rename over the original"; Append streams old rows first.**
`InsertInto` creates `<name>.tmp-<random>` in the **same directory** as the target (same filesystem ⇒ `os.Rename` is an atomic replace on POSIX; on Windows Go's rename maps to `MoveFileEx(MOVEFILE_REPLACE_EXISTING)` — accepted, this project targets and tests POSIX), opens a `pqarrow.FileWriter` on it with `WithStoreSchema()` (see D3), then: for **Append**, streams every batch from a fresh read of the existing file (the provider's own scan machinery), then every batch from the insert reader; for **Overwrite**, streams only the insert reader. On full success: close the writer (finalizing the footer), fsync, rename over the original, return the count of *input* rows consumed. On any error — input stream error, write error, close error — delete the temp file and return the error; the original was never touched. The rename is the commit point required by the engine contract ("commit or roll back before returning"). Alternatives: *rewrite in place* (truncate + write) — rejected outright, any failure destroys the original; *append a second file and treat the table as a directory* — rejected, it changes the provider's data model and every read-side requirement for a write-side convenience; *reject Append entirely and support only Overwrite* — rejected, the rewrite implementation is small, bounded, and exactly as atomic as Overwrite, and append is the common insert mode; the O(file) cost is inherent to the format (documented on the method), not a fragility.

**D2 — Row count is the number of rows consumed from the insert's input stream, both providers, all modes.**
Not "rows now in the table": for Overwrite that would conflate replaced size with written size, and the engine forwards the provider's number verbatim (its design D7) precisely so the provider can report what *it* means by "written". Zero input rows is a valid count of 0. For Parquet Append, a zero-row input short-circuits after draining the reader — no rewrite, no rename, table contents unchanged (the spec requires only unchanged visible contents, and skipping a pointless whole-file rewrite is both safer and cheaper). Zero-row Overwrite does perform the rewrite (an empty file with the schema is the required visible outcome). Iceberg zero-row Append likewise short-circuits without a commit; zero-row Overwrite commits the replacement.

**D3 — Parquet schema fidelity: the writer stores the Arrow schema, and the temp file is written with the provider's registered schema.**
Two failure modes to prevent: (a) the Arrow→Parquet→Arrow round trip deriving a subtly different schema for the rewritten file (post-insert scans would then fail the engine's registered-schema validation); (b) the engine-delivered stream's schema object differing in metadata from the registered schema. For (a), `pqarrow.WithStoreSchema()` embeds the registered Arrow schema in the file so subsequent reads recover it exactly. For (b), the writer is constructed with the provider's own cached registered schema, and incoming batches — guaranteed by the engine to be *logically* in the registered schema — are written against it. Statistics stay enabled (writer default) so row-group pruning keeps working on rewritten files.

**D4 — Iceberg: only the catalog-backed provider type implements `WritableTableProvider`; capability is expressed in the type system, not by erroring at insert time.**
`NewTableProviderFromCatalog` returns a wrapper type embedding the shared provider and adding `InsertInto`; `NewTableProvider` (metadata-location) keeps returning the read-only type. Registration-time type assertion then truthfully reports writability, and an `INSERT` against a metadata-location provider fails with the engine's uniform "does not support inserts" error without a provider round trip. Alternative — one type whose `InsertInto` errors when catalog-less: rejected; it would register every Iceberg table as insert-capable and turn a static capability fact into a runtime error with a provider-specific message, diverging from how the engine treats every other non-writable provider.

**D5 — Iceberg InsertInto: load a fresh table handle via `cat.LoadTable`, then `Table.Append` (append mode) or `Table.Overwrite` with no filter (overwrite mode).**
Loading fresh per insert (the same discipline as per-scan loading) makes each insert commit against the table's latest state rather than a handle cached at construction. `Overwrite` with the default `AlwaysTrue` filter is precisely "replace all visible data in one commit" (verified, Context). The library's commit machinery supplies atomicity (metadata swap via `CommitTable`), conflict retry, and partitioned-write routing; the provider adds nothing on top. Errors from `Append`/`Overwrite` — including input-stream errors surfaced mid-write and commit rejections after retries — return as the insert's error with the table untouched; orphaned data files from failed attempts are accepted (never visible; cleaning them is a maintenance operation out of scope). Alternative — hold and chain the `*Table` returned by `Append`: rejected; the provider would maintain mutable shared state that per-scan loading exists to avoid, for no correctness gain (`LoadTable` returns the committed state anyway).

**D6 — Iceberg schema handling: rely on name-based resolution; do not depend on Arrow field-id metadata surviving the engine.**
The write path resolves the input schema through the table's own name mapping when field ids are absent (verified, Context), and field names match by construction. Field-id metadata embedded in the registered schema may or may not survive the Rust planning round-trip — and a *partial* survival is the dangerous case (ids present on some fields ⇒ conversion error). Defense: the provider wraps the incoming reader to substitute its canonical registered schema, with field-id metadata stripped, so conversion deterministically takes the name-mapping path regardless of what metadata the stream carried. This is a metadata-only substitution on batches whose layout the engine already guarantees; no data is touched. Alternative — pass the stream through untouched and hope ids survive intact: rejected; it makes correctness depend on an FFI metadata property no spec guarantees.

**D7 — Concurrency: a per-provider-instance mutex serializes `InsertInto`; scans never take it.**
Parquet: two concurrent rewrites would race the rename and silently drop one insert's rows — the mutex makes this correctness-critical. In-flight scans hold the old inode's file handle and read it to completion unaffected by the rename (POSIX semantics); scans starting after the rename open the new file — exactly the spec's "pre- or post-insert contents, never torn". Iceberg: the mutex is an optimization, not a correctness need (the catalog arbitrates), but serializing same-instance inserts avoids burning iceberg-go's commit-retry budget on self-inflicted conflicts; scans are snapshot-isolated by construction. The engine's self-insert case (`INSERT INTO t SELECT ... FROM t`) stays deadlock-free: the scan side never touches the insert mutex, and for Parquet the input stream is fully independent of the rename (the scan's reader was opened on the old inode before the insert could commit). Alternative — no lock, document "one insert at a time": rejected for Parquet (silent data loss is not a documentable behavior) and therefore adopted uniformly.

**D8 — Testing mirrors the pushdown wiring's layering: adversarial unit tests for the atomicity/mode logic, then end-to-end and differential coverage.**
(1) Parquet write-path unit tests exercised without the engine, by calling `InsertInto` directly with hand-built readers: mode rejection (Replace), failing-reader injection at first/middle/last batch asserting the original file's bytes are unchanged (hash before/after) and no temp file remains, zero-row append (no rewrite) and zero-row overwrite (empty file), schema round-trip of the rewritten file, concurrent-append serialization, scan-open-before-insert reading old contents to completion. (2) Iceberg unit tests: Replace rejection; metadata-location provider does *not* satisfy `WritableTableProvider` (compile-time/assertion test); failing-reader injection asserting the current snapshot is unchanged and no new snapshot appears; a stub `catalog.Catalog` whose `CommitTable` always fails, asserting the statement errors and a rescan shows pre-insert contents; schema-metadata-stripping wrapper behavior (with and without field-id metadata on the input). (3) End-to-end per provider, once the engine capability exists: register, `INSERT INTO ... VALUES` and `INSERT INTO ... SELECT`, column-subset insert, `INSERT OVERWRITE`, then `SELECT` in the same session asserting exact combined/replaced row sets (hadoop-catalog-backed and partitioned for Iceberg). (4) Differential: after any sequence of inserts, a full scan equals the row multiset computed independently (prior rows ⊎ inserted rows, or replacement), and pushdown queries on rewritten Parquet files still agree with unpruned scans (guards the D3 statistics claim). Direct-call unit tests deliberately do not wait on `add-table-provider-insert` landing; only layer (3) depends on it.

## Risks / Trade-offs

- [Parquet append is O(existing file) per insert] → Inherent to the single-file format (no append API exists — Context); documented on the provider. Batch-streamed on both read and write sides, so memory stays O(batch), never O(file). Callers with heavy append workloads belong on the Iceberg provider.
- [Crash between temp-file completion and rename, or between rename and return] → Worst case is a leftover `.tmp-*` file (never read by scans; name pattern documented) or a completed rename whose statement error was never returned — the file is then valid post-insert content, which is within the "provider defines visibility of its own committed work" contract. No state ever mixes old and new bytes.
- [`os.Rename` non-atomicity off POSIX] → Accepted and stated (D1); CI and the project's platforms are POSIX. No fsync-of-directory is attempted beyond file fsync; a machine crash in the rename window can lose the *insert*, never the original file's integrity on journaled filesystems — consistent with the spec's "original intact on failure" being the load-bearing guarantee.
- [Rewrite drops original encoding niceties (bloom filters, codec choices)] → Correctness-neutral (absent metadata always means "keep" on the read side — pushdown design); called out as a Non-Goal. Differential pushdown tests on rewritten files guard against worse.
- [iceberg-go orphan data files accumulate from failed inserts] → Iceberg-normal behavior; invisible to scans; cleanup (`DeleteOrphanFiles` exists in v0.6.0) is deliberately out of scope.
- [Hadoop catalog under concurrent multi-process writers is only as safe as atomic rename + iceberg-go's retry] → Out of scope by the proposal (single catalog instance, provider-side serialization for same-instance inserts); the spec's concurrency scenarios stay within one provider instance.
- [Engine contract drift: `add-table-provider-insert` is not yet built] → This change is planned against its settled design (interface shape, exactly-once delivery, registered-schema stream, mode plumbing). If the engine change's implementation shifts the interface, this change's tasks rebase on the final signature — the provider-side decisions (atomic rename, catalog commit, mode honesty) are independent of those details. Layer-1/2 tests (D8) don't depend on the engine at all.
- [Field-id stripping (D6) discards ids the engine faithfully preserved] → Harmless: name mapping resolves to the identical field ids (it is derived from the table's own schema); stripping trades a never-worse resolution path for immunity to partial-metadata corruption.

## Migration Plan

Purely additive to both provider packages: existing constructors, read paths, and pushdown behavior are byte-identical for programs that never issue `INSERT`. No FFI, core-package, or dependency changes. Rollback = revert the commits; files or tables written by inserts before a rollback remain valid Parquet/Iceberg data readable by the read-only providers.

## Open Questions

- Whether Parquet writer properties (compression codec, dictionary settings) should be caller-configurable at construction — deferrable; defaults are correct, and a `NewTableProvider` options parameter is an independent, additive follow-up.
- Whether Iceberg inserts should pass snapshot properties (e.g. a `wrote-by` marker) — cosmetic, deferrable; `nil` properties are what the repo's own fixture writes use today.
