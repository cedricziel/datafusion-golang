# Design: wire-parquet-and-iceberg-pushdown

## Context

See proposal.md — Why. The engine side is finished (`add-table-provider-pushdown`): a provider that implements `datafusion.PushdownTableProvider` receives, per scan, a `*ScanOptions` with `Projection []int` (indices into the registered schema; nil ⇒ all, empty ⇒ zero columns), `Filters []Expr` (implicit AND; the closed AST in `datafusion/expr.go`: `Compare`, `IsNull`, `Between`, `InList`, `And`, `Or`, `Not` over `Column{Name, Index}` and typed `Literal`), and `Limit int64` (-1 ⇒ none). Projection is a hard contract (the engine validates the returned stream schema and does not re-project); filters are advisory (`Inexact` — the engine re-applies every one); the limit is a hint. The binding constraint from `openspec/specs/table-provider/spec.md`: a provider "MAY use pushed filters only to omit rows that cannot satisfy them; it MUST NOT be required to evaluate any filter for the query to be correct" — and, symmetrically, it must never omit a row that *can* satisfy them.

Verified facts about the pinned libraries (from `go doc` and vendored sources in the module cache, not memory):

**`arrow-go` v18.7.0, Parquet side:**

- `file.Reader.MetaData() *metadata.FileMetaData`; `FileMetaData.RowGroup(i) *RowGroupMetaData`; `RowGroupMetaData.NumRows() int64`, `.ColumnChunk(i) (*ColumnChunkMetaData, error)` (i = Parquet **leaf column** index).
- `ColumnChunkMetaData.Statistics() (TypedStatistics, error)` returns **nil, nil when stats are absent or untrustworthy**: `StatsSet()` internally checks `IsSetStatistics()`, rejects `schema.SortUNKNOWN` sort orders, and gates on `AppVersion.HasCorrectStatistics(...)` — the known-bad-writer guard (old writers wrote signed-order min/max for strings/decimals) is already applied for us. `TypedStatistics` exposes `HasMinMax()`, `HasNullCount()`, `NullCount()`, `NumValues()`, `Descr() *schema.Column`; the concrete types (`BooleanStatistics`, `Int32Statistics`, `Int64Statistics`, `Float32Statistics`, `Float64Statistics`, `ByteArrayStatistics`, `FixedLenByteArrayStatistics`, ...) add typed `Min()`/`Max()`.
- `schema.Column` exposes `PhysicalType()`, `LogicalType()`, `SortOrder()` — needed to interpret raw min/max for unsigned and temporal logical types.
- `pqarrow.FileReader.GetRecordReader(ctx, colIndices, rowGroups []int)`: both nil ⇒ all. `colIndices` are **Parquet leaf indices**, not Arrow field indices (`checkCols` validates against `MetaData().Schema.NumColumns()`). `rowGroups` is exactly the list of row-group indices to read — passing a subset **is** the pruning mechanism. Internally `SchemaManifest.GetFieldIndices(colIndices)` maps leaves to their top-level Arrow field roots, **deduplicated in first-appearance order** — so leaf indices supplied in projection order yield output columns in projection order. `FileReader.Manifest.Fields []SchemaField` (top-level, parallel to the Arrow schema) with `Children []SchemaField` / `ColIndex int` (-1 unless leaf) provides the Arrow-field→leaf-indices mapping.
- Bloom filters: `file.Reader.GetBloomFilterReader() *metadata.BloomFilterReader`; `.RowGroup(i) (*RowGroupBloomFilterReader, error)`; `.GetColumnBloomFilter(leafIdx) (BloomFilter, error)` returns **nil, nil when the column chunk has no bloom filter** (offset ≤ 0). `metadata.TypedBloomFilter[T parquet.ColumnTypes]` is a struct embedding `BloomFilter`, constructible directly (`&TypedBloomFilter[int64]{bf}`), with `Check(v T) bool` hashing the **physical** value bytes. `parquet.ColumnTypes = bool | int32 | int64 | float32 | float64 | Int96 | ByteArray | FixedLenByteArray`.

**`iceberg-go` v0.6.0:**

- `Table.Scan(opts ...ScanOption) *Scan` with `table.WithRowFilter(e iceberg.BooleanExpression)`, `table.WithSelectedFields(fields ...string)`, `table.WithLimit(n int64)`, `table.WithCaseSensitive(b bool)`. The existing provider already calls `scan.ToArrowRecords(ctx)`.
- **`WithRowFilter` genuinely unlocks metadata-level pruning** (verified in `table/scanner.go` and `table/arrow_scanner.go`): `PlanFiles` (1) projects the row filter onto each partition spec and deletes whole **manifests** whose partition summaries cannot match (`buildManifestEvaluator`, `slices.DeleteFunc` over the manifest list); (2) applies a partition evaluator and `newInclusiveMetricsEvaluator` (per-data-file column min/max/null stats from manifest entries) to skip individual **data files**; (3) at read time, `arrow_scanner.go` additionally applies `newParquetRowGroupStatsEvaluator` and `newBloomFilterPredicates` to skip **row groups inside Parquet data files**, and finally filters **rows** with the bound expression. So one converted expression buys four pruning levels, all library-side.
- Expressions: package `iceberg` — `Reference("name")` (an unbound column term), `EqualTo/NotEqualTo/LessThan/LessThanEqual/GreaterThan/GreaterThanEqual[T LiteralType](term, v)`, `IsNull/NotNull(term)`, `IsIn/NotIn[T LiteralType](term, vals...)`, `NewAnd/NewOr(l, r, ...)`, `NewNot(child)`. `LiteralType = bool | int32 | int64 | float32 | float64 | Date | Time | Timestamp | TimestampNano | string | []byte | uuid.UUID | Decimal | variant.Value`. `iceberg.BindExpr(schema, expr, caseSensitive)` binds an expression against a schema and errors on unknown fields / unconvertible literals.
- Projection semantics: `WithSelectedFields` → `Schema.Select(caseSensitive, names...)` → `PruneColumns` — the projected schema keeps **table-schema order**, not the requested order. `ToArrowRecords` returns batches in that projected schema (fields referenced only by the row filter are read for filtering but not included in the output).

## Goals / Non-Goals

**Goals:**

- Real skipped work: projected-away Parquet columns never decoded; provably-non-matching Parquet row groups never read; Iceberg manifests/data files that cannot match never opened.
- The skip logic is provably one-directional and tested adversarially in isolation: pruning may only remove data that *cannot* match; every uncertain input keeps the data.
- Bloom-filter pruning for equality/IN predicates in `providers/parquet` (the OTel-style point-lookup case: `trace_id = '...'`), included because the v18.7.0 API is clean (see D5).
- Zero new dependencies; zero changes to the core `datafusion` package or the FFI.

**Non-Goals:**

- `Exact` filter reporting or any engine-side change — the engine's advisory/re-filter contract stays as is.
- Extending the predicate AST (decimals, LIKE, functions) — different change.
- Manual Iceberg manifest/statistics handling outside `iceberg-go`'s own scan machinery — the library already does manifest, data-file, row-group, and row-level pruning off one expression (Context); duplicating any of it would add correctness risk for zero gain.
- Parquet page-index (column/offset index) pruning — a finer-grained sibling of row-group skipping; deferrable until row-group skipping proves insufficient.
- Parallel/multi-range Parquet reads, remote object stores, snapshot selection.

## Decisions

**D1 — Parquet projection: map Arrow field indices to Parquet leaf indices via `FileReader.Manifest`, and pass them to `GetRecordReader` in projection order.**
`ScanOptions.Projection` indexes the registered Arrow schema (top-level fields); `GetRecordReader` wants Parquet leaf indices. For each projected field index `i`, collect the leaf `ColIndex` values under `Manifest.Fields[i]` (a top-level primitive field is itself a leaf; a nested field contributes all its leaves). Concatenate in projection order: `GetFieldIndices` dedups roots in first-appearance order, so the output schema comes back in exactly the requested order — no re-projection wrapper needed for the normal case. Empty non-nil projection (zero columns, row counts only): `GetRecordReader` with empty indices would read everything, so instead read the single cheapest column (fewest total compressed bytes across surviving row groups) and wrap with `datafusion.ProjectReader(reader, [])`, which yields zero-column batches with correct row counts. Alternative — always read full-width and use `ProjectReader`: rejected, it decodes every column and forfeits the entire projection win; `ProjectReader` remains the fallback only for the zero-column case.

**D2 — Row-group skipping is a pure, typed skip-evaluator over an abstracted per-column stats view; the only question it answers is "can this row group be *proven* empty of matches?".**
Shape: `canSkip(expr Expr, stats rowGroupStats) bool`, where `rowGroupStats` is a small provider-internal abstraction (per column: optional typed min/max, optional null count, row count) filled from `ColumnChunkMetaData.Statistics()` — and constructible by hand in unit tests without any Parquet file. Returning `false` is always correct; `true` requires proof. Rules (satisfaction semantics: a row "satisfies" a predicate iff it evaluates to SQL TRUE — NULL comparisons never satisfy):

- `And(l, r)`: skip if `canSkip(l) || canSkip(r)`. `Or(l, r)`: skip only if `canSkip(l) && canSkip(r)`.
- `Not(e)`: rewritten into the leaves before evaluation — `Not(Compare)` flips the operator, `Not(IsNull)` toggles negation, `Not(Between/InList)` toggles `Negated`, `Not(And/Or)` applies De Morgan, `Not(Not(e))` cancels. This is sound under SQL's three-valued logic for *satisfaction*: Kleene negation and De Morgan hold, and a NULL operand fails to satisfy both a predicate and its complement, which only ever errs toward keeping. A `Not` over anything unrecognized ⇒ never skip.
- `Compare` (with min/max present): `eq` skips iff `lit < min || lit > max`; `lt` skips iff `min >= lit`; `lteq` iff `min > lit`; `gt` iff `max <= lit`; `gteq` iff `max < lit`; `neq` skips iff `min == max == lit` (every non-null value equals lit; null rows never satisfy `neq`).
- Any comparison/`Between`/`InList` predicate skips when the column is provably all-null (`NullCount() == RowGroupMetaData.NumRows()`, null count present).
- `IsNull` skips iff null count present and zero; `IsNull{Negated}` (IS NOT NULL) skips iff provably all-null.
- `Between` (inclusive bounds): skips iff `high < min || low > max || low > high`. Negated: satisfied iff `col < low || col > high`, so skips iff `min >= low && max <= high`.
- `InList`: skips iff every list element individually skips as an `eq` (all outside [min,max], or bloom-absent per D5). Negated `InList`: skips iff `min == max` and that single value is in the list.
- Type discipline: the literal must match the column's Arrow type family; the comparison runs in the column's **sort-order domain** — for unsigned logical types (physical int32/int64 storing unsigned bits, `SortOrder() == SortUNSIGNED`) raw min/max are bit-reinterpreted to uint32/uint64 before comparing; utf8/binary compare bytewise-unsigned (Parquet's ByteArray order — truncated min/max written by conforming writers remain valid bounds, so range checks stay safe); timestamps compare as int64 **only when the literal's unit equals the column's unit** (DataFusion coerces literals to the column type, so mismatch is not expected — but on mismatch, keep); date32 as int32. Floats: min/max pruning only when both stats are non-NaN, and a NaN literal never skips. Any mismatch, missing `HasMinMax()`, nil `Statistics()`, or unhandled shape ⇒ keep the row group.

The scan then calls `GetRecordReader(ctx, leafIndices, survivingRowGroups)`; if every row group is skipped, pass an explicit empty selection and return an empty reader with the projected schema (zero rows is a valid result per the engine spec). Alternative — evaluate directly against `TypedStatistics` inline in the scan path: rejected; the abstraction exists precisely so the skip logic gets its own adversarial unit-test suite (spec scenarios: boundary equality at min/max, missing stats, all-null, inconclusive ranges) without file fixtures.

**D3 — Row-group skip decisions use only top-level primitive columns.**
A `Compare`/`Between`/`InList`/`IsNull` on a column whose top-level field is nested (struct/list/map) gets no stats-based decision (keep). The engine's AST cannot express nested-field predicates anyway (literals are primitives, `Column` refers to top-level fields), so this is a guard, not a limitation.

**D4 — Parquet limit hint: a truncating reader wrapper.**
When `Limit >= 0`, wrap the record reader so it stops after the batch that reaches the limit (whole batches only — the engine trims the excess; the contract is "at least that many"). Trivial, and directly benefits filterless `LIMIT n` previews (the only case the engine delivers a limit, per the engine design). Alternative — trim the final batch to exactly the limit: pointless slicing work the engine repeats anyway.

**D5 — Bloom filters are in scope, for `eq` and `InList` probes, with a strict type allowlist.**
The v18.7.0 API is clean: `GetBloomFilterReader().RowGroup(rg)` then `GetColumnBloomFilter(leaf)` — `nil, nil` means no filter (keep); otherwise `(&TypedBloomFilter[T]{bf}).Check(v)` where `false` is a *definite* absence (safe to skip: bloom filters have false positives, never false negatives) and `true` keeps. Probed values must be converted to the column's **physical** representation exactly as the writer hashed them: utf8/binary → `parquet.ByteArray`; int8/16/32 and uint8/16 → widened `int32`; int64 → `int64`; uint32 → bit-reinterpreted `int32`; uint64 → bit-reinterpreted `int64`; date32 → `int32`; timestamp → `int64` in the column's unit (unit mismatch ⇒ no probe). Floats are excluded (`0.0 == -0.0` in SQL but their bit patterns hash differently — probing 0.0 would wrongly skip a group containing only -0.0); bools are excluded (pointless). Probes run only for row groups that survived min/max pruning, and only when the scan actually carries an `eq`/`InList` on a bloom-equipped column — bloom filter reads cost I/O, so absent predicates must not trigger them. This lands now rather than deferred because the API needs no plumbing beyond what D2 already opens (the `file.Reader` is open, leaf indices are known) and it is the mechanism that serves point-lookups on high-cardinality columns (the previously-discussed trace_id/span_id case). Alternative — defer bloom to a follow-up: rejected; the marginal code is one probe function plus its tests, and the correctness argument (one-directional skip) is identical to D2's.

**D6 — Iceberg: convert the AST to one `iceberg.BooleanExpression` and hand everything to `Table.Scan` via `WithRowFilter` + `WithSelectedFields` + `WithLimit`; do no manual pruning.**
Verified (Context): one row-filter expression drives manifest pruning, data-file metrics pruning, in-file row-group/bloom pruning, and row-level filtering inside iceberg-go. The provider's whole filter job is therefore a faithful converter:

- `Compare` → `iceberg.EqualTo/NotEqualTo/LessThan/LessThanEqual/GreaterThan/GreaterThanEqual(iceberg.Reference(col.Name), v)`.
- `IsNull` → `iceberg.IsNull` / `iceberg.NotNull`.
- `Between` → `NewAnd(GreaterThanEqual(low), LessThanEqual(high))`; negated → `NewOr(LessThan(low), GreaterThan(high))` (sound under three-valued logic — a NULL fails both forms).
- `InList` → `iceberg.IsIn` / `iceberg.NotIn`; `And`/`Or`/`Not` → `NewAnd`/`NewOr`/`NewNot`.
- Literals: bool/int32/int64/float32/float64/string/[]byte map directly; int8/16 widen to int32; uint8/16/32 widen to int64; date32 → `iceberg.Date`; timestamps → `iceberg.Timestamp` (µs) for s/ms/µs units and `iceberg.TimestampNano` for ns — all lossless widenings only.
- The scan always sets `WithCaseSensitive(true)` — the registered Arrow field names are the Iceberg schema names verbatim (produced by `SchemaToArrowSchema`), so case-insensitive matching could only introduce ambiguity.

**Faithfulness is correctness-critical here, unlike D2**: iceberg-go row-filters *exactly* with the converted expression — a semantically-off conversion would drop matching rows, which the engine cannot repair. Two guards: (1) conversion is **all-or-nothing per top-level filter** — if any node inside one of the `ScanOptions.Filters` conjuncts fails to convert (unrepresentable literal, e.g. uint64 above int64 range or date64, which cannot occur for schemas iceberg-go itself produced but is guarded anyway), that entire conjunct is dropped; dropping a whole top-level conjunct only widens the scan (safe — the engine re-filters), while dropping a *sub*-expression (e.g. one disjunct of an OR) would narrow it (unsafe, never done). (2) The converted expression is pre-validated with `iceberg.BindExpr(tbl.Schema(), expr, true)` at scan setup; a bind error drops that conjunct rather than surfacing — a pushed filter must never be able to fail a query. Alternative — convert without bind-checking and let `ToArrowRecords` fail: rejected, it converts an advisory optimization into a query-breaking dependency, violating the spec's "MUST NOT be required to evaluate any filter" clause in spirit.

**D7 — Iceberg projection: `WithSelectedFields` prunes the read; `datafusion.ProjectReader` fixes the order.**
`ScanOptions.Projection` indices map through the registered Arrow schema to field names (index-aligned by construction). `WithSelectedFields(names...)` restricts what's read and returned, but the output arrives in table-schema order (`Schema.Select` semantics, Context) while the engine demands the requested order. So: compute the selected-set's schema order, and when it differs from the requested order, wrap with `ProjectReader(reader, perm)` where `perm` maps schema order → requested order. Cheap (column-pointer shuffling per batch, no data copies). Empty non-nil projection: `WithSelectedFields` of zero fields is unspecified in iceberg-go, so select the first schema field and wrap with `ProjectReader(reader, [])` for zero-column, correct-row-count batches (mirrors D1). Alternative — skip `WithSelectedFields` and project full-width batches Go-side: rejected; iceberg-go would read and decode every column of every surviving file, forfeiting the projection win.

**D8 — Testing: each pruning/conversion layer gets its own adversarial unit suite, plus differential provider-level tests.**
Three layers: (1) Parquet skip-evaluator unit tests against hand-built `rowGroupStats` — every operator × {disjoint-below, boundary-at-min, contained, boundary-at-max, disjoint-above, missing stats, all-null, min==max, NaN floats, unsigned extremes, negations, AND/OR compositions}; asserted per-decision (skip/keep), not via query results. (2) Iceberg converter unit tests — AST in, expression out, compared against expected `iceberg.BooleanExpression` values, plus drop-cases (unconvertible literal anywhere in a conjunct ⇒ whole conjunct dropped, bind failure ⇒ dropped). (3) Differential tests per provider: generate fixtures (multi-row-group Parquet files via `pqarrow` with bloom-filter-enabled writer properties; partitioned multi-file Iceberg tables via iceberg-go's write path, as established by the providers' existing tests), then run a battery of queries and assert pushdown-scan results equal engine-filtered full-scan results row-for-row — the spec's "pruned and unpruned scans agree" scenarios. Parquet tests additionally assert real skipping happened (via the chosen row-group list) so pruning can't silently regress to "never skip". Rationale: differential tests prove safety but pass trivially if pruning never fires; the unit suites prove the decisions themselves, including ones fixtures make awkward (unreliable stats, adversarial boundaries).

## Risks / Trade-offs

- [A skip-evaluator bug drops row groups containing matching rows — the engine cannot repair omitted rows, and results are silently wrong] → The evaluator is pure and unit-tested adversarially at boundaries (D8); every uncertain path defaults to keep; differential tests cross-check end-to-end. This is the highest-severity risk in the change and the reason the evaluator is isolated from I/O.
- [Iceberg converter unfaithfulness drops matching rows via iceberg-go's exact row filtering] → All-or-nothing conjunct conversion, lossless-only literal widenings, `BindExpr` pre-validation, differential tests (D6, D8). Note the asymmetry with Parquet: there, conservative-but-wrong only reads too much; here, the converter must be *exact*, so it does strictly structural, lossless mappings and drops everything else.
- [Bloom probe hashes a value differently than the writer did (physical-representation mismatch) ⇒ false "absent" ⇒ wrongly skipped row group] → Strict allowlist of physical conversions (D5), floats excluded outright, and differential tests over files written with bloom filters enabled for every allowed type.
- [Reading bloom filters costs extra I/O that can exceed the benefit on small row groups] → Probes only run for eq/IN predicates on columns that have a filter, and only for row groups already surviving min/max pruning; accepted otherwise — no adaptive heuristics in this change.
- [`GetRecordReader` with an explicit empty row-group list may not mean "read nothing"] → Do not rely on it: the all-skipped case short-circuits before the reader and returns an empty projected-schema reader directly (D2).
- [iceberg-go internals (pruning levels, `Select` ordering) shift under a future version bump] → The observable contract is only "exact projection + never-drop-matching-rows + identical results", all covered by differential tests; ordering is normalized on our side of the boundary (D7), so an ordering change breaks tests, not correctness. Verified facts in Context are re-checked on any iceberg-go bump.
- [Limit-hint truncation interacts with filters] → It can't: the engine only delivers a limit when no filters were pushed (engine design D8); the wrapper is applied regardless and is harmless either way.

## Migration Plan

Purely additive to both provider packages: `Scan` keeps its exact current behavior; `ScanWithOptions` is new, and registration picks it up automatically via the engine's existing interface detection. No FFI, core-package, or dependency changes. Rollback = revert the commits.

## Open Questions

- Whether the Parquet differential fixtures also cover files written by non-arrow writers (e.g. checked-in files from other engines) to exercise the `HasCorrectStatistics` gating path with real foreign metadata — nice-to-have hardening; arrow-go's gate is already unit-testable by constructing `AppVersion` values, so this affects test breadth only, not the approach or tasks.
